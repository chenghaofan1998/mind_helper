# Action Pocket 产品纲领

> 状态：战略方向纲领  
> 适用范围：产品定位、场景选择、产品边界、技术原则与验证纪律  
> 当前阶段：需求验证，尚未证明产品成立  

---

## 一、纲领结论

Action Pocket 不建设新的知识库，也不以搜索、问答或 AI 总结为核心价值。

> **Action Pocket 是“指导性文本的行动层”：把用户已有的攻略、教程、笔记、命令和 SOP，在真正需要时转换成可核对、可执行、可暂停续做的行动卡。**

产品位于“用户已经决定做一件事”和“用户真正开始操作”之间，减少重新查找、阅读长文、提取步骤、替换参数和记忆进度的成本。

Command Pocket 的命令能力不再被视为长期产品边界，而是 Action Pocket 的一个早期验证资产。

---

## 二、要解决的根问题

用户缺少的通常不是内容，而是内容的使用能力：

1. 资料已经收藏，却想不起何时适用；
2. 找到资料后仍要重新阅读和整理；
3. 指导内容中的条件、参数、风险和验证方式分散；
4. 执行被打断后，不知道上次停在哪里；
5. 知识库、攻略和 SOP 保存的是文字，用户真正需要的是下一步行动。

因此，产品不以“收进多少知识”为目标，而以“多少已有内容真正促成行动”为目标。

北极星指标：

> **行动卡被用于完成真实任务的次数。**

---

## 三、产品母机制

所有场景共享同一条闭环：

> **显式需求 → 找到可信原文 → 转换为行动卡 → 用户逐步执行 → 记录结果 → 下次更快使用**

### 3.1 输入对象

只处理具有指导意义的文字内容，包括：

- Obsidian、Logseq 和 Markdown 笔记；
- 工作 SOP、Runbook、操作手册；
- 教程、公众号文章和学习材料；
- 游戏攻略、配装和任务指南；
- 命令行命令及其说明；
- 用户显式粘贴的文本、文件和链接。

### 3.2 输出对象：行动卡

每张行动卡至少包含：

- **目标**：要完成什么；
- **适用条件**：什么情况下使用；
- **前置条件**：开始前需要准备什么；
- **参数**：环境、路径、账号、角色、装备等变量；
- **步骤**：按顺序执行的动作；
- **风险**：需要额外确认的步骤；
- **验证**：如何判断任务完成；
- **来源**：每一步对应的原文位置；
- **进度**：开始、暂停、继续和完成状态。

行动卡不是摘要。摘要帮助理解，行动卡帮助完成任务。

---

## 四、场景与用户

产品长期可以覆盖多个内容场景，但首版必须从一个可验证场景切入。

### 4.1 首发场景：重复发布与环境配置

目标用户：

- 5–30 人的小型技术团队；
- 已有 Markdown Runbook 或 SOP；
- 每周至少执行一次重复流程；
- 流程尚未自动化，仍需人工复制命令、填写参数和核对结果。

介入时刻：

> 用户已经决定执行某个发布或配置流程，准备打开文档并逐步操作时。

选择该场景的原因：

- 使用时刻明确；
- 输入资料已经存在；
- 执行结果可以验证；
- 时间节省和错误率可以量化；
- 风险、参数、进度和来源回链都有真实价值。

### 4.2 第二阶段候选：游戏与软件攻略

目标用户在卡关、配置游戏、安装 Mod 或处理软件故障时，调用置顶行动卡，逐步完成攻略。

该场景只有在首发机制成立后才验证，不进入首版承诺。

### 4.3 第三阶段候选：个人知识与学习材料

用户在写作、做方案或实践某个方法时，从 Obsidian/Logseq 中获得可直接采用的论据、方法和检查清单。

该场景需要更强的跨文档检索与语义判断，不能与首版同时建设。

## 五、产品形态

### 5.1 核心界面

首版采用：

- Windows 托盘应用；
- 全局热键唤出的窄侧栏；
- 一个小型 CLI；
- 当前任务的一张行动卡；
- 原文定位、参数填写、逐步复制、勾选、暂停和继续。

主界面不展示完整知识库，也不提供开放式聊天。

### 5.2 低授权触发

首版只允许用户显式触发：

- 按全局热键；
- 从任务列表选择；
- 通过 CLI 打开；
- 选择文件；
- 主动粘贴文本。

后续可评估：

- 按住说话输入需求；
- 浏览器“发送到 Action Pocket”；
- Agent/MCP 显式调用；
- 产品内部最近任务。

明确禁止默认使用：

- 录屏或截图识别；
- 常驻剪贴板监听；
- 键盘监听；
- 麦克风常驻监听；
- 全量行为捕捉；
- 未经用户确认的后台弹窗。

### 5.3 已有知识库与临时资料

有知识库时，只读接入用户明确选择的文件或目录，不迁移原始资料。

没有知识库时，提供轻量“临时资料箱”：用户可粘贴文本或选择文件，默认只服务当前任务，明确保存后才进入长期资料池。

临时资料箱不是第二套知识库，不提供收藏管理、标签体系、双链、同步和阅读器。

## 六、产品边界

### 6.1 首版必须做

- Markdown 和纯文本解析；
- 行动卡草稿生成；
- 文档拥有者核对和批准；
- 参数定义与填写；
- 步骤逐项复制和勾选；
- 暂停与继续；
- 原文引用和定位；
- 来源变化后的过期提示；
- 风险提示与完成验证；
- 本地使用流水。

### 6.2 首版明确不做

- 通用知识库；
- 全库问答或聊天；
- AI 总结中心；
- 自动执行命令；
- 模型凭空生成高风险步骤；
- 知识图谱；
- 全量 RAG 平台；
- 浏览器抓取、PDF 和复杂 Office 解析；
- macOS、移动端和跨设备同步；
- 账号、团队后台、SSO；
- 语音、Agent 和 MCP；
- 游戏、学习和泛写作专用功能。

---

## 七、安全与信任原则

1. **来源优先**：所有关键步骤必须能回到原文；
2. **模型不越权**：模型可识别结构，不得为高风险流程补写来源中不存在的命令；
3. **人工批准**：正式团队行动卡必须由文档拥有者确认；
4. **变化即失效**：源文件发生变化后，旧行动卡必须标记过期并重新确认；
5. **只复制不执行**：危险命令不得自动粘贴、发送回车或启动 Shell；
6. **本地优先**：索引、卡片和反馈默认保存在本地；
7. **最小授权**：只读取用户明确选择的文件和目录；
8. **可撤销可删除**：授权、索引和使用记录均可查看和删除。

## 八、技术实施纲领

### 8.1 最小架构

```text
显式输入
  ↓
Markdown/纯文本解析
  ↓
行动结构抽取
  ↓
来源跨度与文件哈希校验
  ↓
人工确认
  ↓
行动卡运行器
  ↓
本地结果与反馈流水
```

### 8.2 数据结构

正式行动卡至少保存：

- `sourcePath`、`sourceHash`；
- 目标、条件和参数定义；
- 有序步骤；
- 每一步的原文摘录和位置；
- 风险等级；
- 验证步骤；
- 批准人、批准时间和版本。

运行实例仅保存当前步骤、非敏感参数和完成状态。

### 8.3 模型边界

首版可以使用规则或模型生成草稿，但必须满足：

- 草稿不可直接成为正式卡；
- 命令必须来自连续原文片段；
- 没有验证方式时不得自行补写；
- 云模型调用必须展示并确认发送内容；
- 无模型时仍可人工创建和运行行动卡。

### 8.4 现有资产处理

Command Pocket 可复用：

- Windows 托盘与热键外壳；
- 少量结果、立即行动的交互原则；
- 本地 JSONL 和宽容读写经验；
- 危险确认门；
- 使用反馈和试点纪律。

不可直接沿用：

- 以命令为唯一对象的数据模型；
- 单纯按最近和复制次数排序；
- C# 单文件作为长期核心架构；
- 复制即代表成功的判断。

## 九、实施阶段

### 阶段 0：设计合作验证

开发前必须找到 5 个符合条件的合作团队，并取得真实 Markdown Runbook。

若找不到，不立项开发。

### 阶段 1：8 周试点版

建议投入：2 名 Windows/.NET 工程师 + 0.5 名产品设计。

交付范围：

- Windows 托盘侧栏；
- CLI；
- 单份 Markdown/纯文本输入；
- 行动卡生成、确认、运行和续做；
- 来源校验、过期处理和本地流水。

### 阶段 2：2–4 周真实验证

每个合作团队至少执行 10 次真实流程，不以演示任务代替。

### 阶段 3：相邻场景扩展

只有首发场景通过验证，才允许依次测试：

1. 游戏及软件配置攻略；
2. Obsidian/Logseq 个人知识使用；
3. 语音输入、浏览器分享、Agent/MCP；
4. 多来源检索与跨文档行动卡。

每次只增加一个场景或一个能力，并重新设定生死线。

---

## 十、验证与关停纪律

首发试点通过线：

- 开始正确第一步的时间下降 ≥30%；
- 完整流程完成率 ≥70%；
- 无原文来源的高风险步骤为 0；
- 两周后重复使用团队 ≥60%；
- 至少 3 个团队愿意继续使用；
- 至少 1 个团队给出包含预算决策人的付费意向。

立即关停条件：

- 出现无来源的高风险步骤；
- 产品必须依赖高权限监听才能产生价值；
- 用户仍普遍选择直接阅读原文或使用现有工具；
- 无法在开发前找到 5 个设计合作团队；
- 未达到核心节时和重复使用指标。

不允许通过增加聊天、自动监听、更多连接器或扩大用户范围掩盖验证失败。

---

## 十一、长期愿景

如果核心机制被验证，Action Pocket 将成为各种指导性文字的统一运行界面：

> 用户不再为了行动重新阅读整篇资料，而是在需要时获得来源可信、步骤清楚、风险可控的下一步。

长期壁垒不来自内容数量或模型能力，而来自：

- 高质量的“文字到行动”结构；
- 来源与版本可信度；
- 跨场景的执行反馈；
- 少授权、低打扰的调用体验；
- 对错误、过期和风险的保守处理。

在这些能力被真实使用数据证明之前，Action Pocket 始终是一项待验证假设，而不是已经成立的平台。
