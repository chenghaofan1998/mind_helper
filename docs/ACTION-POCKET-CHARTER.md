# Action Pocket 项目纲领

> 本文是本项目最高优先级文档，约束产品定位、范围和后续实现。
> 其他文档、历史方案与本文冲突时，以本文为准。需求价值仍待真实使用验证。

## 一、一句话定位

**Action Pocket 是连接知识库与日常任务的统一轻量入口：随手记进去，需要时拿出来，变成自己看得懂、用得上的内容。**

它既是知识输入入口，也是知识输出入口；不绑定某一种知识库软件，不替代已有知识库，也不另建一套知识库。

Logseq 是当前验证起点，不是产品边界。未来可按真实需求接入 Obsidian、其他知识库软件，以及企业级 RAG（检索增强生成）引擎；这些是扩展方向，不代表已经支持或首版全部交付。

核心承诺：

> 有东西想记，方便存进去；忘了怎么做，给出可照做的内容；忘了怎么理解，找回当时听懂的那一段。

## 二、为什么做

当前用户使用 Logseq 保存 AI 讨论和学习笔记，已有 embedding 与 rerank。

主要问题不是资料不够多，而是：

- 输入需要整理和搬运，容易打断当前事情。
- 学过的命令和知识过段时间会忘，使用时不容易快速找回。
- 检索到长笔记后，仍要翻找、理解，才能真正使用。
- AI 重新解释不一定比自己以前认可的解释更容易理解。

我们优先缩短“想记 → 保存”和“需要 → 用上”的距离，而不是追求更多收藏或更多生成内容。

## 三、输入与输出如何形成闭环

### 输入：先接住，再整理

- 用户主动输入文字、粘贴 AI 对话或选择已有文本。
- 先快速保存，整理可以稍后做，不要求每次填很多字段。
- AI 可以建议标题、归属和整理结果，但不能擅自覆盖或删除原笔记。
- 保留原始内容与来源；特别保留困惑、类比、算例和纠错过程，不能只剩规范化摘要。
- 允许轻量标记“这段我懂了”“以后给我看这段”。
- 写入哪个知识库、什么位置、按什么规则保存，须明确；只有确认写入成功才显示已保存，失败时保留输入并明确提示。

### 输出：优先找回，必要时转化

- 用户用当前问题调用知识，不必记住原笔记标题。
- 优先返回过去保存或认可的内容，不默认重新生成一篇回答。
- 需要实际操作时，可转成命令、步骤或检查清单。
- 原始记录、本次改写和补充推断必须区分；关键内容可回到对应知识源的原文。
- 缺少依据或存在冲突时明确说明，不用流畅回答掩盖缺口。

### 反馈：只留下值得复用的结果

- 结果操作保持为打开/复制定位与复制原文/命令；在没有明确消费工作流前不展示固定或“有用”反馈。
- 输出默认服务当前任务，不自动全部回存，避免制造新的囤积。
- 值得保存的成果经用户确认后写入指定知识库，并关联原始材料。

## 四、一个入口，多种输出

首选形态是**热键唤出的轻量浮窗**：能快速记录、提问、复制、查看原文，必要时置顶。输入和查询意图不明确时让用户选择，不悄悄写入。

| 场景 | 用户需要 | 输出方式 |
|---|---|---|
| Find、Docker 等命令 | 忘了写法，知道要做什么 | 命令、关键参数、注意事项、来源 |
| Adam 等知识概念 | 找回自己理解过的解释 | 理解片段、必要上下文、当时的例子 |
| 工作 TODO | 快速查看未完成事项 | 按知识源提供的原始任务状态查询的列表，不支持时明确说明 |
| 游戏或软件攻略 | 操作时持续参考 | 可置顶的步骤与进度 |
| 分析决策 | 用已有知识比较与判断 | 依据、选项、限制和知识缺口 |

这些场景共享入口与来源能力，但不强行统一成聊天回答或步骤卡。

## 五、首版范围与优先级

**首版做小闭环：快速记入知识库 + 命令调用 + 理解片段找回。**

先用当前 Logseq 和已有检索服务验证一条完整链路；产品与核心逻辑不绑定 Logseq。新增知识源逐个验证，不先建设庞大的连接器平台。

必须具备：

1. 显式文字输入和粘贴，保留原始内容，可靠写入明确位置。
2. 接入首个知识源与现有检索能力，将来源接入与输入、检索结果展示等核心逻辑分开，不重新建设知识库。
3. 自然语言查询，呈现少量可用结果和原文入口。
4. 命令可复制，概念解释可展开必要上下文。
5. 轻量浮窗、当前项目切换与可核验的原文打开/复制定位能力。

后续按真实需求逐项验证：TODO 查询、攻略置顶与进度、分析决策。

首版不做全格式导入、网页攻略抓取、知识图谱、复杂 Agent、自动执行命令、多端同步、团队审批后台或全量行为监听。不为了展示效果同时建设所有场景。

## 六、技术与信任边界

- **内容以其所属知识源为准。** 可以接入多个来源，但不另维护一套独立正文；本地索引是可重建的派生数据，临时输入和使用偏好不是第二套知识库。
- 接入按能力区分：读取、检索、写入、原文定位、状态查询不一定全部具备。只读来源只用于输出；输入须指定可写知识库，不能把检索接口当作写入接口。
- 优先复用已有 embedding、rerank 或知识源提供的检索服务，不要求用户更换底层引擎；保留必要的标题、段落或块层级上下文，不能只靠固定长度切块。
- 旧固定/反馈存储不得形成正文副本且不再展示；来源更新或删除后不能把任何旧定位冒充最新内容。
- 企业 RAG 接入是后续独立验证项：必须遵守原系统身份与文档权限、数据隔离和审计要求；缓存与生成结果也不能绕过权限。不得将个人本地原型直接宣称为企业可用。
- “我理解的解释”优先展示，但不等于内容正确；发现错误需明确纠正。
- 命令区分原记录和本次适配，展示关键环境与参数；危险操作在复制前确认，只复制、不执行。
- 不默认读取剪贴板、屏幕、键盘或麦克风。只处理用户明确授权的内容。
- 云模型发送哪些内容必须透明并经授权；敏感数据不写入日志。

## 七、怎么判断有用

使用真实日常任务验证，不以模拟团队、生成字数或收藏数量证明产品价值。

重点看：

- 输入是否比现在更省事，且没有丢失原文或增加整理负担。
- 从产生问题到获得可用内容，是否比直接搜索原知识库或问通用 AI 更快。
- 找回旧解释是否更容易理解，命令是否真正被正确采用。
- 核对、修改和维护的总成本是否降低。
- 下一次遇到类似需求，用户是否主动再次使用。

先用少量真实命令和概念笔记验证，再扩大范围。没有改善时，先定位输入整理、检索上下文或呈现问题，不靠增加功能掩盖。

## 八、后续工作的执行规则

- 每接入一个知识源，先确认存储形态、接口、读写权限、检索与来源定位能力，再决定实现；当前 Logseq 需先区分文件型 graph 和 DB 版本。
- 新增 Obsidian、其他知识库或企业 RAG 接入，以真实用户需求和接口可行性为依据；不把首个接入对象的专有结构写死到核心模型，也不为尚未验证的商业化场景提前建设企业平台。
- 桌面平台依据实际工作和游戏设备确认，不因已有 Windows 代码直接锁定。
- 每次只推进一个可验证闭环；拿不准先问，不替用户决定产品边界。
- 已验证原型中的命令交互、热键与本地存储经验可以复用，但不能据此扩大当前产品范围。
- 旧“团队发布 / Runbook 执行器”纲领及其试点门槛已被本文替代；历史材料已从工作树移除，需要时可从 Git 历史查阅。
- 后续代码、设计与验收都应能回答：**这项改动怎样让知识更容易记入，或更容易在需要时用上？**
